# Requirements Document

## Introduction

This feature adds `apps/crypt`, a Next.js web app (App Router, TypeScript strict mode) with two pages:

- The **Ouija_Simulator** at `/` is the main demo. Hackathon judges and visitors type a message on a retro button-phone (T9 multi-tap keypad or a normal keyboard) and get the reply as SMS parts that arrive one by one, each labelled with its part number and the GSM-7 or UCS-2 encoding. No phone and no login are needed. Messages go through the same `@lazarus/brain` Gateway_Pipeline that the Necromancer_App uses, so HELP, STOP, START, QUESTION, SCAM, REMIND, LIST, CANCEL and the English, Urdu and Roman Urdu replies behave as they do over real SMS.
- The **Crypt_Dashboard** at `/crypt` is a read-only page that explains how the gateway works and shows fixed Demo_Counters and a Sample_Conversation in which every phone number is masked.

The work is split the same way as the other specs:

- `packages/brain` is reused as it is. The Crypt_App calls existing exports (`runGatewayPipeline`, `applyChanges`, `decideDelivery`, `finalizeDelivery`, `splitSms`, `detectEncoding`, `getPartLimits`, `countCodeUnits`, `detectLanguage`, `maskNumber`, `maskPhoneNumbers`, `redactSecrets`, `createMemoryCache`, `FIXED_TEXTS`, `GATEWAY_TEXTS`, `DEFAULT_SETTINGS`, `zeroCounters`, `localDayKey`, `encodeReminder`, `decodeReminders`) and `createGeminiClient` from the `@lazarus/brain/gemini` subpath. The Crypt_App contains no command routing, language detection, SMS splitting, reminder time parsing or answer logic of its own.
- `apps/crypt` holds the T9_Decoder and T9_Encoder (pure TypeScript), the React UI, the Simulator_Route handler and the Ip_Rate_Limiter.

This document extends the brain-command-router, sms-message-splitter, ai-answer-service, sms-reminders and necromancer-sms-gateway specs. Terms defined in those specs (Gateway_Pipeline, Gateway_State, Gateway_Decision, Canonical_Number, Command, Command_Router, Language, Language_Detector, SMS_Splitter, Reply_Text, Reply_Parts, Answer_Service, Try_Later_Text, Slow_Down_Text, Help_Text, Welcome_Back_Text, Rate_Limiter, Daily_Send_Cap, Outcome, Stop_List, Reminder, Reminder_Slot, Reminder_Text, Due_Time, Late_Window, Delivery_Decision, Delivery_Outcome, Reminder_Delivery_Text, Pakistan_Time, Number_Masker, Masked_Number, Gemini_Api_Key, Heartbeat) keep their meaning.

### Decisions made in this document

These decisions were made without asking, to produce a first version. Each one can be changed at review.

- **Routes.** The Ouija_Simulator is the home page `/`. The Crypt_Dashboard is `/crypt`. The Simulator_Route is `POST /api/ouija`.
- **The server is stateless; the browser holds the session.** Vercel serverless functions do not keep memory between calls, so the browser keeps the Simulator_Session in page memory and sends a Session_Snapshot with each request. The Simulator_Route rebuilds a Gateway_State from the Session_Snapshot, runs the brain, and returns the updated Session_Snapshot. Reloading or closing the tab ends the Simulator_Session and drops its Reminders. Nothing is written to `localStorage`, `sessionStorage`, cookies or a database.
- **One fixed server-side Simulator_Number.** The Gateway_Pipeline needs a Canonical_Number as the sender. The Simulator_Route uses one fixed fictional Simulator_Number that is defined only in server code and never appears in any response. The Session_Snapshot carries no phone number.
- **Gateway settings in the simulator are the brain's DEFAULT_SETTINGS** with Allowlist_Mode off and no Own_Number. The Ouija_Simulator has no settings screen.
- **Per-IP limit of 30 requests per 10 minutes.** The Ip_Rate_Limiter allows at most 30 Simulator_Requests per Client_Ip in any 600,000-millisecond sliding window and keeps its counts in the memory of each server instance. On Vercel, separate instances keep separate counts (see Known limitations). This limit sits in front of the per-number Rate_Limiter of the Gateway_Pipeline, which still applies to the Simulator_Session. The per-IP limit is the guard for the shared Gemini free quota.
- **New session resets only the visitor's own simulated session.** The New_Session_Button lets a judge who hit STOP, the per-number Rate_Limiter or the Daily_Send_Cap keep testing. It runs only in the browser, because the browser holds the Session_Snapshot: it sends no Simulator_Request, does not count against the Ip_Rate_Limiter and does not reset the Ip_Rate_Limiter. The Gemini quota stays protected by the per-IP limit on the Simulator_Route, which New session cannot clear.
- **The per-number limits stay at the brain's DEFAULT_SETTINGS** (`perNumberLimit` 5 per `rateWindowMinutes` 60, `dailySendCap` 200 parts), so the demo shows the real gateway behaviour, including the Slow_Down_Text, instead of a relaxed demo mode.
- **Replies_Left is derived from brain exports.** The brain has no export that returns a remaining count. The Simulator_Route computes Replies_Left from `DEFAULT_SETTINGS`, the Session_Snapshot receive times and day counters, and the brain's `countInWindow` and `countersFor`, with the formula in the Glossary. The Crypt_App has no rate window or limit value of its own. Messages the Rate_Limiter does not check (STOP, and messages ignored while STOP is on) do not use up Replies_Left.
- **Initial Replies_Left comes from DEFAULT_SETTINGS.** Before the first Simulator_Response of a Simulator_Session, the Ouija_Simulator shows Replies_Left as `DEFAULT_SETTINGS.perNumberLimit` (5), imported from `@lazarus/brain`, because an empty Session_Snapshot has 0 receive times and 0 parts handed.
- **New session clears the thread.** Pressing New session removes all bubbles from the Phone_Screen and shows only the Status_Note `New session started.`, the same way the reset after an invalid Session_Snapshot clears it.
- **Message_Body length is 1 to 480 UTF-16 code units.** 480 is about 3 GSM-7 SMS parts, which keeps the demo close to real SMS and bounds Gemini prompt size.
- **No time travel.** Reminders are delivered at their real Due_Time while the page is open. A judge can try `REMIND in 1 minute drink water` to see a delivery during a demo.
- **T9 keypad types Latin text only.** Urdu script is typed with the normal keyboard. The keypad supports lower case, upper case and digits.
- **Reply parts arrive 700 milliseconds apart** so viewers can see them arrive one by one.
- **Phone-number-like digit runs in response text are masked.** The Simulator_Route passes every reply part and Reminder_Text it returns through the brain's `maskPhoneNumbers`, including text the visitor typed, so no string the browser receives from the Simulator_Route holds 7 or more digits in a row.

### Known limitations

- **Per-IP limit is per server instance.** Vercel can run several instances of the Simulator_Route; each counts requests on its own, so a visitor can exceed 30 requests per 10 minutes across instances. A shared store would need a paid or external service, which the tech rules do not allow.
- **Session_Snapshot can be edited by the visitor.** The visitor controls the browser, so the visitor can change the Session_Snapshot (for example to clear the STOP status). The Simulator_Route validates its shape and limits, and the Ip_Rate_Limiter guards the Gemini quota. This affects only the visitor's own demo session.
- **New session is a client-side reset.** Any visitor can clear the per-number Rate_Limiter, Daily_Send_Cap and STOP status of their own Simulator_Session with the New_Session_Button. The per-number limits therefore show real gateway behaviour but do not protect the Gemini quota; only the Ip_Rate_Limiter does.
- **Replies_Left is a snapshot at Server_Time.** The sliding Rate_Limiter window can free a reply later without a new request. The Replies_Left_Indicator updates only when the next Simulator_Response arrives.
- **Reminders need an open tab.** A background tab can delay browser timers. A Reminder whose delivery is checked more than the Late_Window after its Due_Time expires, as on the real gateway.
- **The Gemini free tier is shared.** When the shared quota is used up, every visitor gets the Try_Later_Text for QUESTION and SCAM until the quota resets.

## Glossary

- **Crypt_App**: The Next.js web app in `apps/crypt`, an npm workspace of the monorepo named `@lazarus/crypt`.
- **Ouija_Simulator**: The page of the Crypt_App at `/` that shows the Phone_Mock, sends Message_Bodies to the Simulator_Route and shows Simulated_Replies.
- **Crypt_Dashboard**: The read-only page of the Crypt_App at `/crypt` that explains the gateway and shows Demo_Counters and the Sample_Conversation.
- **Phone_Mock**: The retro button-phone UI of the Ouija_Simulator, made of the Phone_Screen, the T9_Keypad, the Compose_Field, the Send_Key, the Clear_Key and the New_Session_Button.
- **New_Session_Button**: The Phone_Mock button with the visible text and accessible name `New session` that performs a Session_Reset.
- **Session_Reset**: The client-side steps that start a new empty Simulator_Session, defined in Requirement 19 criterion 2. A Session_Reset sends no Simulator_Request.
- **Replies_Left**: The number of further messages the per-number Rate_Limiter and the Daily_Send_Cap allow in the Simulator_Session at the Server_Time. It is 0 when `countersFor(counters, today).handed` is greater than or equal to `DEFAULT_SETTINGS.dailySendCap`, and otherwise `max(0, DEFAULT_SETTINGS.perNumberLimit − countInWindow(receiveTimes, Server_Time, DEFAULT_SETTINGS.rateWindowMinutes × 60,000))`, where `receiveTimes` and `counters` come from the Session_Snapshot after the request was handled and `today` is `localDayKey(Server_Time, 300)`. An integer from 0 to `DEFAULT_SETTINGS.perNumberLimit` (5).
- **Replies_Left_Indicator**: The text next to the Phone_Mock that shows `Replies left: n of 5`, where n is the latest Replies_Left and 5 is `DEFAULT_SETTINGS.perNumberLimit`.
- **Phone_Screen**: The area of the Phone_Mock that shows the conversation thread: sent Message_Bodies, Simulated_Replies, Reminder deliveries and Status_Notes.
- **T9_Keypad**: The 12 on-screen keys `1` to `9`, `*`, `0` and `#` of the Phone_Mock.
- **Key_Map**: The fixed characters of each T9_Keypad key in Letter_Mode: `1` → `.`, `,`, `?`, `!`, `'`, `-`, `1`; `2` → `a`, `b`, `c`, `2`; `3` → `d`, `e`, `f`, `3`; `4` → `g`, `h`, `i`, `4`; `5` → `j`, `k`, `l`, `5`; `6` → `m`, `n`, `o`, `6`; `7` → `p`, `q`, `r`, `s`, `7`; `8` → `t`, `u`, `v`, `8`; `9` → `w`, `x`, `y`, `z`, `9`; `0` → space, `0`. In Upper_Case the letters are the upper-case forms.
- **Letter_Mode**: The T9_Keypad mode in which keys `0` to `9` cycle through their Key_Map characters, in Lower_Case or Upper_Case.
- **Number_Mode**: The T9_Keypad mode in which each press of key `0` to `9` types that digit once.
- **Lower_Case** and **Upper_Case**: The two letter cases of Letter_Mode.
- **Key_Event**: One press of a T9_Keypad key, made of the key and the press time in milliseconds.
- **Multi_Tap_Timeout**: 1,000 milliseconds. A press of the same key within the Multi_Tap_Timeout of the previous press moves to the next character of that key; a later press starts a new character.
- **Pending_Character**: The character shown, marked as not yet committed, while the Multi_Tap_Timeout of the last press runs.
- **T9_Decoder**: The pure function in the Crypt_App that turns a sequence of Key_Events and a starting mode into text.
- **T9_Encoder**: The pure function in the Crypt_App that turns a T9_Text into a sequence of Key_Events which the T9_Decoder decodes back to that T9_Text.
- **T9_Text**: A string made only of characters that appear in the Key_Map (lower and upper case letters `a` to `z`, the digits `0` to `9`, space and `.`, `,`, `?`, `!`, `'`, `-`).
- **Input_Mode**: Which input the Phone_Mock uses: Keypad_Input (the T9_Keypad) or Keyboard_Input (typing in the Compose_Field with a physical or on-screen keyboard).
- **Compose_Field**: The text area of the Phone_Mock that holds the Message_Body being written.
- **Message_Body**: The text the visitor sends, 1 to 480 UTF-16 code units long, containing at least 1 non-whitespace character.
- **Send_Key**: The Phone_Mock key that sends the Message_Body.
- **Clear_Key**: The Phone_Mock key that deletes the last character of the Compose_Field.
- **Simulator_Route**: The Next.js route handler at `POST /api/ouija` that runs on the Node.js runtime and calls the brain for the Ouija_Simulator.
- **Simulator_Request**: The JSON body of a request to the Simulator_Route: either a `message` request with a Message_Body and a Session_Snapshot, or a `deliver` request with a Reminder_Id and a Session_Snapshot.
- **Simulator_Response**: The JSON body of a successful Simulator_Route reply: the Reply_Parts, the Reply_Encoding, the Command, the Language, the Outcome or Delivery_Outcome, the updated Session_Snapshot, the Replies_Left and the Server_Time.
- **Simulator_Session**: The state of one open Ouija_Simulator tab, kept in page memory: the conversation shown on the Phone_Screen and the latest Session_Snapshot.
- **Session_Snapshot**: The part of the Gateway_State that belongs to the Simulator_Session, as JSON with no phone number: the STOP status, the Rate_Limiter receive times, the last Slow_Down_Text time, the day counters and the Active_Reminders without their Canonical_Number.
- **Snapshot_Parser**: The pure function in the Crypt_App that validates a Session_Snapshot and turns it into the Gateway_State of the Simulator_Session, or returns a validation error.
- **Snapshot_Printer**: The pure function in the Crypt_App that turns the Gateway_State of the Simulator_Session into a Session_Snapshot.
- **Simulator_Number**: The one fixed fictional Canonical_Number that the Simulator_Route uses as the sender of every Simulator_Session. Defined only in server-only code.
- **Simulated_Reply**: The Reply_Parts of one Simulator_Response as shown on the Phone_Screen.
- **Reply_Encoding**: `GSM-7` or `UCS-2`, the encoding the brain's `detectEncoding` reports for the Reply_Text of a Simulated_Reply.
- **Part_Badge**: The label on each shown part of a Simulated_Reply: `Part n of N`, the Reply_Encoding, and the code units used out of the part limit (for example `148/153`).
- **Status_Note**: A short line on the Phone_Screen that is not an SMS and explains why no reply came (for example after STOP), styled differently from SMS parts.
- **Server_Time**: The Simulator_Route clock in milliseconds since the Unix epoch at the time of the response.
- **Ip_Rate_Limiter**: The in-memory limiter in the Simulator_Route that allows at most 30 Simulator_Requests per client IP address in any 600,000-millisecond (10-minute) sliding window.
- **Client_Ip**: The first address in the `x-forwarded-for` request header, or the literal `unknown` when the header is absent.
- **Demo_Counters**: Fixed example numbers shown on the Crypt_Dashboard (messages received, replies sent, SMS parts sent, ignored messages), stored as constants in the Crypt_App and labelled as demo data.
- **Sample_Conversation**: A fixed example exchange of 4 to 8 messages shown on the Crypt_Dashboard, stored as constants in the Crypt_App, in which every sender is shown only as a Masked_Number of a fictional number.
- **Theme_Tokens**: The colors, font, radius and spacing of `.kiro/steering/design.md`: background `#0B0F0C`, surface `#141A16`, text `#E6F2E9`, muted `#8FA396`, soul green `#39FF88`, ember `#FFB347`, blood `#FF4D5E`, radius 14, spacing 4/8/12/16/24/32.
- **Browser_Payload**: Everything the Crypt_App sends to a browser: HTML, JavaScript and CSS files, JSON responses and response headers.
- **Crypt_Test_Suite**: The Vitest tests of the Crypt_App, including fast-check properties.
- **Smoke_Test**: The Playwright test that runs against a production build of the Crypt_App started with no Gemini_Api_Key.
- **Reminder_Horizon**: 30 days (2,592,000,000 milliseconds, the brain's `REMINDER_HORIZON_MS`), the longest time from receive time to Due_Time that the brain accepts for a Reminder.
- **Clock offset**: The Server_Time of the latest Simulator_Response minus the browser clock at the moment that response arrived, in milliseconds.
- **Corrected clock**: The browser clock plus the Clock offset, used by the Ouija_Simulator to schedule Reminder checks.
- **Error state**: The Phone_Mock state shown after a request fails as in Requirement 6 criterion 5: the error text in the blood color with the visible label `Error`.
- **Delivery_Outcome names**: The brain's Delivery_Outcomes `reminder-sent`, `reminder-stopped`, `reminder-not-allowed`, `reminder-capped`, `reminder-expired` and `reminder-failed`. In the simulator Allowlist_Mode is off and every part is treated as sent, so `reminder-not-allowed` and `reminder-failed` do not occur in practice.

## Requirements

### Requirement 1: App setup and deployment

**User Story:** As a maintainer, I want the Crypt_App to build and deploy on the Vercel free tier from the monorepo, so that judges can open the demo with a link.

#### Acceptance Criteria

1. THE Crypt_App SHALL be a Next.js App Router project in `apps/crypt` with the package name `@lazarus/crypt`, listed in the `workspaces` of the root `package.json`, written in TypeScript with `strict` set to true in its TypeScript configuration, and containing no explicit or implicit use of the type `any` in its source and test files, so that the Crypt_App `lint` script reports 0 errors for the type `any`.
2. THE Crypt_App SHALL import brain logic only from the entry points `@lazarus/brain` and `@lazarus/brain/gemini`, with no import of any other path inside `packages/brain`.
3. THE Crypt_App SHALL import `@lazarus/brain/gemini` only from server-only modules, meaning modules that are never part of a client component's import graph, so that no file in the client build output contains code from `@lazarus/brain/gemini`.
4. THE Crypt_App SHALL provide the npm scripts `test` (Vitest single run, never watch mode), `typecheck`, `lint`, `build` and `e2e` (Playwright), and each script SHALL exit with code 0 when its checks pass and with a non-zero code when any check fails.
5. THE root `package.json` SHALL run the Crypt_App `test` and `typecheck` scripts in addition to the existing brain scripts, and IF any of these scripts exits with a non-zero code, THEN THE root script SHALL exit with a non-zero code.
6. THE Crypt_App SHALL read no environment variable other than `GEMINI_API_KEY` and `GEMINI_MODEL`, SHALL read both only from server code, and the root `.env.example` SHALL list both with empty values.
7. IF `GEMINI_MODEL` is missing or empty, THEN THE Crypt_App SHALL use the brain's default model chosen by `createGeminiClient`, with no model name of its own.
8. WHEN `next build` runs with or without `GEMINI_API_KEY` and `GEMINI_MODEL` set, THE Crypt_App SHALL build with exit code 0, and IF the build has a TypeScript or lint error, THEN `next build` SHALL exit with a non-zero code.
9. THE Crypt_App SHALL declare the Node.js runtime for the Simulator_Route and SHALL run on the Vercel free tier with no paid service, no database, no external storage and no service other than the Gemini free tier.
10. WHEN a visitor with no cookies sends an HTTP GET request to `/` or `/crypt`, THE Crypt_App SHALL respond with HTTP status 200 and the page content, with no redirect to a login page, no account prompt and no `Set-Cookie` header.
11. THE Crypt_App SHALL set no cookie in any response, including Simulator_Route responses.

### Requirement 2: Phone mock layout

**User Story:** As a judge, I want a phone that looks like an old button phone, so that I understand how a real Sender uses Lazarus.

#### Acceptance Criteria

1. THE Ouija_Simulator SHALL show the Phone_Mock with the Phone_Screen, the Compose_Field, the 12 T9_Keypad keys in 4 rows of 3 (`1 2 3`, `4 5 6`, `7 8 9`, `* 0 #`), the Send_Key, the Clear_Key, the New_Session_Button, the Replies_Left_Indicator and one control to switch the Input_Mode, all visible without horizontal scrolling at viewport widths from 320 to 1920 CSS pixels.
2. THE Ouija_Simulator SHALL show, beside the Phone_Mock at viewport widths of 768 CSS pixels or more and below the Phone_Mock at narrower widths, a list of exactly 10 example messages, each shown as its full text and stored as constants in the Crypt_App: `HELP`, one free question that the Command_Router routes to QUESTION, one `SCAM <text>` message, `REMIND in 1 minute drink water`, `LIST`, `CANCEL 1`, `STOP`, `START`, one Roman Urdu message for which `detectLanguage` returns `roman-ur`, and one Urdu script message for which `detectLanguage` returns `ur`, each 1 to 480 UTF-16 code units long.
3. WHEN the visitor activates an example message, THE Ouija_Simulator SHALL discard any Pending_Character, replace the whole Compose_Field text with the example text, update the counter of criterion 6, and send no Simulator_Request.
4. THE Phone_Screen SHALL show each sent Message_Body as an outgoing bubble, and each part of a Simulated_Reply, each Reminder delivery part and each Status_Note as a separate incoming bubble, in the order they are added, with the newest at the bottom.
5. WHEN a bubble is added to the Phone_Screen, THE Phone_Screen SHALL scroll so that the whole new bubble is visible inside the Phone_Screen.
6. THE Ouija_Simulator SHALL show, directly under the Compose_Field, the counter `n/480`, where n is the number of UTF-16 code units of the Compose_Field text plus any Pending_Character, and SHALL update n within 100 milliseconds of every change to that text.
7. WHEN the Phone_Screen adds the first part of a Simulated_Reply, THE Phone_Screen SHALL show next to that part the Language label `English` for `en`, `Urdu` for `ur` or `Roman Urdu` for `roman-ur`, taken from the Language of the Simulator_Response, and SHALL show no Language label on later parts or on Status_Notes.
8. THE Input_Mode control SHALL show the current Input_Mode as the visible text `Keypad` or `Keyboard`, and the Phone_Mock SHALL start every new Simulator_Session in Keypad_Input with the T9_Keypad in Lower_Case Letter_Mode.

### Requirement 3: T9 keypad input

**User Story:** As a judge, I want to type with multi-tap like on a button phone, so that I feel the real Sender experience.

#### Acceptance Criteria

1. WHILE the Input_Mode is Keypad_Input and the T9_Keypad is in Letter_Mode, WHEN the visitor presses key `0` to `9` and no Pending_Character of that key is shown, THE Phone_Mock SHALL show, at the end of the Compose_Field text, the first Key_Map character of that key in the current case (Lower_Case or Upper_Case) as the Pending_Character, matching the Pending_Character the T9_Decoder returns for the Key_Events so far, and underlined so that it can be told apart from committed text.
2. WHILE the Input_Mode is Keypad_Input and the T9_Keypad is in Letter_Mode, WHEN the visitor presses the same key as the previous press less than the Multi_Tap_Timeout (1,000 milliseconds) after the previous press, THE Phone_Mock SHALL replace the Pending_Character with the next character of that key in the Key_Map and SHALL wrap from the last character to the first (for example, 5 presses of key `2` show `a`, and 3 presses of key `0` show a space).
3. WHILE the Input_Mode is Keypad_Input, WHEN at least 1,000 milliseconds and at most 1,100 milliseconds have passed since the last press with no other press, or the visitor presses a key other than the key of the Pending_Character, THE Phone_Mock SHALL commit the Pending_Character to the end of the Compose_Field, remove its underline, and, if the press was on key `0` to `9`, start a new Pending_Character for that key as in criterion 1.
4. WHILE the Input_Mode is Keypad_Input and the T9_Keypad is in Number_Mode, WHEN the visitor presses key `0` to `9`, THE Phone_Mock SHALL append that digit to the end of the Compose_Field at once and show no Pending_Character, so that N presses of one key append that digit N times.
5. WHILE the Input_Mode is Keypad_Input, WHEN the visitor presses `*`, THE Phone_Mock SHALL commit any Pending_Character, switch Letter_Mode between Lower_Case and Upper_Case, and add no character to the Compose_Field. If the T9_Keypad is in Number_Mode, the new case SHALL apply when the T9_Keypad returns to Letter_Mode.
6. WHILE the Input_Mode is Keypad_Input, WHEN the visitor presses `#`, THE Phone_Mock SHALL commit any Pending_Character, switch the T9_Keypad between Letter_Mode and Number_Mode, keep the current case, and add no character to the Compose_Field.
7. WHILE the Input_Mode is Keypad_Input, THE Phone_Mock SHALL show the current T9_Keypad mode on the Phone_Screen as exactly one of `abc` (Letter_Mode, Lower_Case), `ABC` (Letter_Mode, Upper_Case) or `123` (Number_Mode), and SHALL update it before the next key press is handled after `*` or `#` is pressed.
8. WHEN the visitor presses the Clear_Key, THE Phone_Mock SHALL remove the Pending_Character if one is shown and leave the committed text unchanged; otherwise it SHALL remove the last code point of the Compose_Field, so that a surrogate pair is removed whole; and IF the Compose_Field is empty with no Pending_Character, THEN THE Phone_Mock SHALL leave the Compose_Field unchanged.
9. WHILE the Input_Mode is Keypad_Input and keyboard focus is on the T9_Keypad, WHEN the visitor presses the physical key `0` to `9`, `*` or `#`, Backspace, or Enter, THE Phone_Mock SHALL act exactly as if the matching T9_Keypad key, the Clear_Key, or the Send_Key (as defined in Requirement 6) was pressed, and SHALL use the time of the physical key press as the Key_Event press time.
10. THE T9_Keypad SHALL show on each key its digit and the letters of its Key_Map entry in the current case (for example `2` with `abc`, `7` with `pqrs`, `1` with `.,?!'-`, `0` with a space symbol), as on a button phone.
11. WHEN the Ouija_Simulator starts a new Simulator_Session, THE T9_Keypad SHALL start in Letter_Mode with Lower_Case and no Pending_Character, and the mode indicator SHALL show `abc`.
12. IF a commit or a Number_Mode digit would make the Compose_Field longer than 480 UTF-16 code units, THEN THE Phone_Mock SHALL drop that character, leave the Compose_Field at its current text, and show the message `Messages can be up to 480 characters.` as in Requirement 5 criterion 4.

### Requirement 4: T9 decoding and encoding

**User Story:** As a developer, I want T9 decoding to be a tested pure function, so that the keypad types exactly what the visitor intends.

#### Acceptance Criteria

1. THE T9_Decoder SHALL take a sequence of 0 to 300 Key_Events, each with a key from the 12 T9_Keypad keys and a press time in whole milliseconds from 0 to 2^53 − 1, together with a starting mode (Lower_Case Letter_Mode, Upper_Case Letter_Mode, or Number_Mode with a remembered letter case). It SHALL return the committed text, the final mode and the Pending_Character (or none). It SHALL depend on no browser API, timer or clock, and SHALL return the same output every time it gets the same input.
2. WHILE the T9_Decoder is in Letter_Mode, WHEN a key `0` to `9` is pressed and the previous Key_Event was the same key with a press time 0 to 999 milliseconds earlier (less than the Multi_Tap_Timeout), THE T9_Decoder SHALL add that press to the current character group. The character of the group SHALL be the one at position (number of presses in the group − 1) modulo the number of Key_Map characters of that key. Letters SHALL be in the current case, and digits and punctuation SHALL be the same in both cases.
3. WHILE the T9_Decoder is in Letter_Mode, WHEN a key `0` to `9` is pressed and either the previous Key_Event was a different key (including `*` or `#`) or the press is 1,000 milliseconds (the Multi_Tap_Timeout) or more after the previous press of the same key, THE T9_Decoder SHALL commit the character of the current group, if there is one, to the committed text and start a new character group with this press.
4. WHEN `*` or `#` is pressed, THE T9_Decoder SHALL first commit any Pending_Character. `*` SHALL switch between Lower_Case and Upper_Case. In Number_Mode the new case is kept and applies when Letter_Mode resumes. `#` SHALL switch between Letter_Mode and Number_Mode. WHILE the T9_Decoder is in Number_Mode, each press of key `0` to `9` SHALL append that digit to the committed text once, with no Pending_Character, whatever the press times.
5. WHILE no Multi_Tap_Timeout is applied at the end of the sequence, THE T9_Decoder SHALL return the character of the last open Letter_Mode group as the Pending_Character and leave it out of the committed text. It SHALL return no Pending_Character when the sequence is empty, ends in Number_Mode, or ends with `*` or `#`.
6. IF the press times of the Key_Events are not non-decreasing, or a press time is negative or not an integer, THEN THE T9_Decoder SHALL return a validation error and no text. Two Key_Events with equal press times SHALL count as 0 milliseconds apart.
7. THE T9_Encoder SHALL take a T9_Text of 0 to 200 characters and return a sequence of Key_Events that starts in Lower_Case Letter_Mode. The first press time SHALL be 0 and the press times SHALL be non-decreasing. The sequence SHALL use `*` before each letter whose case differs from the current case. Presses inside one character group SHALL be spaced 1 to 999 milliseconds apart, and two consecutive characters on the same key SHALL be separated by a gap of at least 1,000 milliseconds.

IF the Simulator_Route responds with HTTP status 400, 405, 413, 429 or 500, THEN THE Simulator_Route SHALL include no Session_Snapshot, no Replies_Left and no Reply_Parts other than the Slow_Down_Text of Requirement 10 criterion 4, so that the Ouija_Simulator keeps its previous Session_Snapshot.

### Requirement 10: Per-IP rate limit

**User Story:** As a maintainer, I want to limit requests per visitor, so that one visitor cannot use up the shared Gemini free quota.

#### Acceptance Criteria

1. WHEN the Simulator_Route receives a POST Simulator_Request whose body is at most 16 kilobytes, THE Ip_Rate_Limiter SHALL decide accept or reject for the Client_Ip after the method check of Requirement 7 criterion 9 and the body size check of Requirement 7 criterion 8, and before the body is parsed as a Simulator_Request, the Session_Snapshot is parsed, or the Gateway_Pipeline or Gemini is called.
2. WHEN the Ip_Rate_Limiter accepts a Simulator_Request, THE Ip_Rate_Limiter SHALL record the Server_Time of that request for the Client_Ip, whatever HTTP status the Simulator_Route later returns for that request (200, 400 or 500), and SHALL NOT record a request it rejects, a request rejected with HTTP status 405 or a request rejected with HTTP status 413.
3. IF a Client_Ip has 30 recorded request times within the sliding window of the 600,000 milliseconds before and including the current Server_Time, THEN THE Simulator_Route SHALL respond to the next Simulator_Request of that Client_Ip with HTTP status 429, a JSON body with an `error` code, no Session_Snapshot, no Replies_Left, and a `Retry-After` header holding the whole number of seconds, rounded up, from the current Server_Time until the oldest of those 30 times is 600,000 milliseconds old, with a value from 1 to 600, and SHALL NOT call the Gateway_Pipeline or Gemini.
4. WHEN the Simulator_Route responds with HTTP status 429 to a body that parses as JSON of the `message` type with a string Message_Body of 1 to 480 UTF-16 code units, THE Simulator_Route SHALL include in the JSON body the Slow_Down_Text from `@lazarus/brain` in the Language that `detectLanguage` gives for that Message_Body.
5. IF the Simulator_Route responds with HTTP status 429 to a body that does not meet the conditions of criterion 4 (not JSON, a `deliver` request, or a missing or out-of-range Message_Body), THEN THE Simulator_Route SHALL include in the JSON body the English Slow_Down_Text, or no Slow_Down_Text for a `deliver` request, and SHALL still respond with HTTP status 429 and the `Retry-After` header of criterion 3.
6. WHEN the Ouija_Simulator receives an HTTP status 429 response to a `message` Simulator_Request, THE Ouija_Simulator SHALL show the Slow_Down_Text from the response as one incoming bubble marked as a Status_Note, keep the outgoing bubble of the sent Message_Body, keep the previous Session_Snapshot unchanged, end the SENDING state and enable the Send_Key.
7. WHEN the Ouija_Simulator receives an HTTP status 429 response to a `deliver` Simulator_Request, THE Ouija_Simulator SHALL show no bubble, keep the previous Session_Snapshot unchanged, and retry as defined in Requirement 13 criterion 8.
8. WHEN the Ip_Rate_Limiter handles a request, THE Ip_Rate_Limiter SHALL first remove every request time 600,000 milliseconds or more older than the current Server_Time and every Client_Ip with no request time left, so that its state holds at most 30 times per Client_Ip and at most 10,000 Client_Ips.
9. IF the Ip_Rate_Limiter must record a request of a new Client_Ip while 10,000 Client_Ips are stored, THEN THE Ip_Rate_Limiter SHALL drop the stored Client_Ip whose newest request time is the oldest, choosing the Client_Ip that sorts first by string comparison when several share that time, and then record the new request.
10. THE Ip_Rate_Limiter SHALL be a pure function of its state, the Client_Ip and the current time in milliseconds, returning the accept or reject result, the new state and, on reject, the `Retry-After` seconds, and FOR ALL sequences of 0 to 500 requests with non-decreasing times, THE Ip_Rate_Limiter SHALL accept at most 30 requests of one Client_Ip in any 600,000-millisecond window (invariant property).
11. FOR ALL sequences of 0 to 500 requests with non-decreasing times from 1 to 50 Client_Ips, THE Ip_Rate_Limiter SHALL give the same accept or reject result and the same `Retry-After` seconds for each request of one Client_Ip as it gives when the requests of all other Client_Ips are removed from the sequence (isolation property).
12. THE Ip_Rate_Limiter SHALL treat all requests with the Client_Ip `unknown` as one Client_Ip.

### Requirement 13: Reminders in the simulator

**User Story:** As a judge, I want to set a reminder and see it arrive, so that I see REMIND, LIST and CANCEL work.
